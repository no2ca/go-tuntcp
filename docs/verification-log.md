# 検証の記録

[CLAUDE.md](../CLAUDE.md) の「検証」の方針が、うまくいっているかを確かめるための記録。

確かめたい仮説は次のとおり。

- 人間が差分を全部読まなくても、「仕様 ↔ テストの意図 ↔ 証拠」の対応を確かめることで、正しさを保てる
- 仕様と文書から説明できないコードを、少なく保てる
- 機能と実装の対応を、粒度を変えて説明できる
- 上の 3 つによって、ほかの方法で個人開発を進めたときと同じ水準に、より速く、人間の認知の負荷を下げながら届く

完璧な検証は目指していない。比べる相手は「全部のコードを自分で読み書きする個人開発」である。

新しいものを上に足す。1 件は次の形で書く。

```
## 日付  タスク  種類
- やったこと:
- 結果:
- 方針への影響:
```

種類は、対応表の確認、抜き取り、予想の確認、あとで見つかった誤り、負荷の気づき、方針の変更のどれか。
「負荷の気づき」には、報告が長すぎた、確認が面倒だった、逆に楽だった、といった人間の感想を書く。

## 2026-11-11  T4-4〜T4-7  あとで見つかった誤り

- やったこと: 先にコミットしてあったテスト 7 件を通す実装をした
- 結果:
  - 先に書いたテストそのものに誤りが 2 つあった: `TestHandle_MultipleConnections` は、ISS を差し替えたあとで `testISS` を前提にした `establish` を呼び、2 本目（別のポート）の返信を 1 本目のポートを前提にした `mustReply` で検査していた。どんな実装でも通らないテストだった。実装の前は別の理由（RST が未実装）でも落ちていたので、気づけなかった
  - 前回の記録にあった「RCV.NXT をまたぐデータを捨てる」は、対話で「まるごと捨てる」と決め、`docs/design.md` に書いた
- 方針への影響: 「落ちてから通す」で見るのは、落ちる理由が確かめたいことと合っているかまで。落ちる理由が 2 つ以上あるテストは、1 つ目を直すまで残りが見えない。今回は失敗の出力に 3 行出ていた（`Seq = 1000100, want 1000000` など）ので、出力を 1 行ずつ読めば実装の前に分かった

## 2026-11-11  T4-3  あとで見つかった誤り

- やったこと: 新しい方針での最初のタスク。RFC 9293 3.10.7.4 First を読み、Table 6 の境界値テストを先に書いて落とし、実装して通した
- 結果:
  - ロードマップの誤り: `Established_UnexpectedSeq` の 4 つすべてが T4-3 で通ると書いてあったが、2 つは First では受理できるセグメントで、T4-7 まで通らない。RFC の表と見比べて分かった
  - 実機確認の誤り: `task e2e` が、実装と関係なく落ちた。前回の `tcpdump.err` が残っていると、tcpdump の起動を待たずに `curl` を始めてしまう不具合だった。M0 では 1 回ずつしか実行しておらず、見つけられなかった
  - 既存のテストが、仕様より単純な挙動を前提にしていた: RCV.NXT をまたぐデータを「捨てる」としているが、RFC は新しい部分だけ処理するとしている。T4-7 で決める
- 方針への影響: 機械的な確認そのものにも誤りがある。落ちたときに「実装が悪い」と決めつけず、記録を読んで原因を分ける必要がある。記録を残す形にしておいたので、原因はすぐ分かった

## 2026-11-11  （タスクなし）  方針の変更

- やったこと: 検証の方針を初めて書き、その日のうちに 4 点を直した
- 結果:
  - 「実装を 1 か所ずつ壊してテストが落ちるかを見る」をやめ、「テストを先に書いて落ちるのを見てから実装する」に変えた。壊して戻す手数が多く、落ちた状態が履歴に残らないため
  - 人間の確認を、毎タスク一律から、タスクの中身に合わせた増減に変えた。抜き取りと予想の確認はマイルストーンの終わりに回した
  - 外の仕様がない振る舞いは、実装の前に対話で決めて `docs/design.md` に書くことにした
  - 記録の置き場所をこのファイルにした
- 方針への影響: 「空の実装で落ちる」は、壊す確認より弱い。判定の境界の取り違えは見つけられないので、境界の値のテストを必須にして補った。これで足りるかは、まだ分からない
